# 사용자 정의 상태

디자이너가 `행동 모드 → 평상시 / 수련 / 잠입`, `소속 → 무소속 / 문파`처럼 상태 그룹과 값을 정의한다. 엔진의 planning·narrative·battle 단계와 별개다. 이미 있는 활동·장소를 복제해 상태로 관리할 필요는 없다.

## 제작 흐름

1. Qt 편집기의 디자인 메뉴에서 **사용자 정의 상태…**를 연다.
2. **＋ 상태**를 누르고 이름, 공용/캐릭터별 범위, 값 이름과 새 게임 초기값을 지정한다. 내부 ID는 자동 생성되며 이름 변경에도 유지된다.
3. 활동·공통 행동·사건의 효과 편집기에서 **상태 변경**을 선택하고 상태와 값을 이름으로 고른다.
4. 사건 발생 조건, 행동 실행 조건, 분기, 표시 조건에는 **상태 확인**을 연결한다. 다른 조건과 AND/OR/NOT로 조합할 수 있다.
5. 화면 요소의 **조건별 표현**에 같은 상태 확인 조건을 연결하면 화면과 배치를 유지한 채 문구·이미지·애니메이션 컨트롤러를 바꿀 수 있다. 처음 일치하는 표현이 적용되고 불일치하면 기본 표현으로 돌아온다.

캐릭터별 상태는 기존 캐릭터별 데이터(`character-v1`) 설정을 사용한다. 효과와 조건의 대상은 행동 실행자 또는 지정 캐릭터다. 실행자가 없는 화면에서는 지정 캐릭터를 선택한다. 각 캐릭터의 초기값은 그룹 초기값으로 시작하며 이후 독립적으로 변경된다. 캐릭터마다 다른 초기값을 직접 지정하는 UI는 이번 범위에 포함하지 않는다.

값/상태를 삭제하거나 소유 범위를 변경해서 사용 중인 연결을 깨뜨리는 경우 관리 창에서 저장을 거부하고 참조 위치를 표시한다. 취소는 원본을 유지한다. 동시에 프로젝트가 변경되면 오래된 관리 창이 새 변경을 덮어쓰지 못한다. 외부 도구로 작성한 데이터도 공통 스키마·의미 검증에서 동일하게 검사한다.

## 데이터와 실행 계약

- 프로젝트: 선택적 `stateGroups[{id,name,scope,initialValueId,values:[{id,name}]}]`. 최대 128그룹, 그룹당 128값.
- 조건: `{op:"stateIs",stateGroupId,stateValueId,owner?}`.
- 효과: `{op:"setState",stateGroupId,stateValueId,owner?}`.
- `owner`는 기존 `{kind:"actor"}` 또는 `{kind:"character",characterId}`. 공용 그룹에서는 생략하고 캐릭터 그룹에서는 필수다.
- 실행 상태: 선택적 `customStates:{shared:{groupId:valueId},characters:{characterId:{groupId:valueId}}}`.
- 변경 기록: `{kind:"state",source,stateGroupId,characterId?,before,after}`. 값은 ID로 기록하고 표시에는 이름을 사용한다.

그룹 ID, 그룹 내 값 ID의 중복, 없는 초기값/참조, 범위와 대상 불일치를 진단한다. 효과는 기존 명령 트랜잭션 안에서 처리하므로 뒤의 비용·효과가 실패하면 전체 명령이 취소된다. 상태만 바꾸는 행동도 `rejectNoEffect` 검사에서 유효한 변화로 계산한다. 평가나 화면 표현은 상태와 난수를 바꾸지 않는다.

상태 그룹을 선언하지 않은 기존 프로젝트에는 실행 상태 필드가 추가되지 않는다. 저장은 기존 결정적 명령 재생과 결과 대조를 사용한다. 같은 콘텐츠에서 중간 저장·불러오기를 지원하며, 콘텐츠 버전이 바뀐 저장은 기존 마이그레이션 절차를 거쳐야 한다. 상태 이름 변경은 ID를 유지하지만 콘텐츠 지문은 변경된다.

Windows/웹 내보내기는 `custom-states-v1` 지원 여부를 검사하여 구형 런타임으로 잘못 내보내는 것을 차단한다. 모바일·콘솔 검증 완료를 의미하지 않는다.

## 검증

- 계약·의미 검증 89개 통과. 예전 스키마 개수에 고정되어 있던 테스트와 도감 데이터 시험에 섞여 있던 화면 의존성을 정리했다.
- 상태·참조 탐색 9개 통과: C++/TypeScript 동등성, 두 캐릭터의 서로 다른 활동과 상태, 공통 행동 비용과 실패 롤백, 사건 효과, 저장 재생·변조 거부, 잘못된 값·대상·초기값, 기존 저장 형태, 참조의 읽기/쓰기 구분.
- 저장·조건별 표현·내보내기 회귀 22개 통과. 별도 구형 런타임 차단 시험 3개 통과(Windows/웹의 상태 지원 검사 포함).
- Qt 실제 UI 자동화로 상태·값 생성 → 활동 효과 → 사건 발생 조건·선택 후 효과 → 한 화면의 상태별 문구를 제작하고 프로젝트 저장·재열기를 확인했다. 사용 중인 그룹 삭제 차단·취소도 확인했다. 기존 조건/효과 편집과 활동 편집·undo/redo 회귀 2개 통과.
- GUI 제작 결과를 외부 JSON 수정 없이 내보냈다. Windows 실제 플레이에서 두 선택 경로의 사건·엔딩과 중간/엔딩 저장, 새 프로세스 복원을 기준 상태와 대조했다. Chrome/Wasm에서는 평상시 → 수련 → 연회 상태와 문구 전환, 각 상태의 파일 다운로드/업로드 저장 복원을 확인했다.
- 실제 제작 중 발견한 두 문제도 수정했다: 활동의 복합 효과를 편집할 때 `target:null`을 삽입하던 오류, 상태/캐릭터 데이터만 바꾸는 공통 행동이 `rejectNoEffect`로 거부되던 오류.
- TypeScript 코어·플레이어·기존 Electron 편집기 타입 검사, 공개 콘텐츠 경계 검사 통과.

- Windows 게임: `.cache/custom-states/windows-final/RaisingPlayer.exe`
- 웹 게임: `.cache/custom-states/web-final`
