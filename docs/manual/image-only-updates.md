# Verified presentation updates without resetting saves

The editor can publish revised interface paint, geometry, unbound interface text and existing image bytes while retaining a previously published game's exact save/replay identity. This is an explicit reviewed choice in Export.

Save the edited project. In Export choose **Preserve saves for a presentation update**, select the previous published `game.json`, optionally select an original player save, then check the changes. Review the changed fields and explicitly choose to use the verified update. A check does not silently enable it. Changed paths, target, source revision, baseline bytes and sample bytes are checked again before publication. Cancelling an alternate review keeps the previously selected review; Clear returns to ordinary export.

The conservative shared policy in `config/presentation-policy.json` permits existing screen/element geometry, paint and style properties, authoring labels, and text on unbound text/button elements. Both snapshots must have valid fingerprints and complete asset checksums. Rules, dialogue/story, actions, conditions, IDs, element order, bindings, unknown fields, asset definitions, audio/font bytes and plugin documents/runtimes must match. Variants and component overrides are deliberately not automatically classified as safe. Unsupported edits require the ordinary content-update/migration workflow.

For API callers, pass the previous `game.json` as `presentationBase` to `exportGame`, alongside a newly validated `content` snapshot and freshly prepared plugins. Layout/text updates require a player advertising `presentation-visual-updates-v1`; an old runtime is rejected instead of silently dropping the new appearance. Image-only exports retain the earlier compatible format.

The exported `content` remains the complete, unchanged baseline snapshot. The native and browser renderers use a separately verified visual overlay for the view only. Commands, event nodes, animation clocks, gallery captures and saves remain subject to the player's normal strict replay checks. Historical gallery captures retain their historical presentation. This does not accept arbitrary old fingerprints or rewrite player saves. A validated sample establishes that sample's replay validity, not a claim that every historical save has been tested.

`game.json` and `export.json` additionally record `presentationRevision`, containing the new source fingerprint and each changed image's baseline/current SHA-256. For these images the effective packaged checksum is `presentationRevision.images[id].sha256`; for unchanged project assets it is `content.assetHashes[id]`. Export still checks every copied source file against the new validated snapshot. The baseline content's checksums describe the original content identity, not revised pixel files. Plugin-generated assets retain their existing plugin checksums.

The receipt distinguishes the effective save `contentFingerprint` from the edited `sourceContentFingerprint`. The project ZIP reopens and verifies against the edited source fingerprint, while the packaged game continues to use the published save baseline. Keep both releases for rollback. Image revisions still require the same asset IDs and paths; sprite rectangles and animation documents cannot change under this policy. Localization entries must match; existing translations may therefore override revised source UI text.

Validation includes contract rejection tests, stale-review checks, editable-backup restoration, and actual native/Web players displaying revised UI while loading, continuing, resaving and freshly restoring the original history. Run `tests/visual/presentation-update.test.mjs`, `tests/journey/presentation-revision.test.mjs`, `tests/qt-studio/presentation-updates.test.mjs`, and `tests/journey/presentation-update-players.test.mjs`. Test the game's own manual/automatic saves and presentation clocks before release.
