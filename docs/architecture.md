# 일정 기반 육성 엔진 설계

이 엔진은 프린세스 메이커 계열의 일정·성장·조건부 사건을 작은 팀이 제작하는 데 집중합니다. 인간은 표·폼·대본 편집기를 사용하고 LLM은 같은 JSON 데이터를 읽거나 구조화된 도구로 수정합니다. 규칙과 이야기를 입력하면 실행할 수 있고, 예상과 다른 결과에는 원인을 설명할 수 있어야 합니다.

## 제품 범위

육성 대상은 한 명입니다. 주변 인물과 해당 인물에 대한 관계 수치는 여러 개를 정의할 수 있습니다. 시간은 1년 12개월, 한 달 3기간이며 시작 연도·월과 총 개월 수는 프로젝트가 지정합니다. 하루·요일·실시간 경과는 계산하지 않습니다.

월초 상태 확인 → 세 기간 일정 예약 → 기간별 활동 → 조건부 사건과 선택 → 다음 기간 → 최종 사건 종료 → 엔딩 판정 순서로 진행합니다. 활동은 수업·일·휴식 등을 하나의 형식으로 표현합니다.

| 포함 | 제외 |
| --- | --- |
| 능력치·자원·컨디션·인물 관계 | NPC끼리의 관계망, 다수 인물 동시 육성 |
| 조건·효과·활동 성공 판정 | 임의 코드 실행, 사용자 플러그인 |
| 배경·인물 이미지·대사·선택·음향 | 자유 이동, 전투, 장비, 제작, 농사 |
| 상태 지정 테스트·재현·사건 설명 | 모든 경로의 자동 도달 가능성 증명 |
| Windows 제작 도구와 플레이어 | 첫 버전의 모바일·콘솔 지원 |

일반 사건은 회차당 한 번, 기간당 최대 한 건 발생합니다. 사건 호출·반복 대본·동시 사건 처리도 초기 범위에서 제외합니다.

## 기술 선택

| 계층 | 결정 |
| --- | --- |
| 제품 언어 | TypeScript, 엄격한 타입 검사 |
| 편집기와 기본 게임 화면 | React, HTML, CSS |
| 데스크톱 호스트 | Electron |
| 개발 빌드 | Vite, electron-vite |
| 설치 파일 | electron-builder 안정판 |
| 원본과 구조 검사 | JSON, JSON Schema Draft 2020-12, Ajv |
| 자동화 | Node CLI, 로컬 stdio MCP |
| 향후 제품 테스트 | Vitest, Playwright |

Electron은 편집기·게임·화면 없는 도구가 같은 TS 코어를 사용하기 쉽게 합니다. 배포 크기·메모리 사용량·브라우저 런타임 업데이트 비용은 작은 검증판에서 측정합니다. 앱 크기가 중요한 제약이 되면 Tauri를, 탐험·전투가 주력이 되면 Godot 또는 Phaser를 재평가합니다.

현재 표현 범위에서는 React와 CSS를 사용합니다. 다수 스프라이트나 GPU 효과가 실제로 필요해지면 PixiJS를 검토합니다. 처음부터 범용 렌더러 추상화·플러그인 시스템을 만들지 않습니다.

## 목표 저장소 구조

```text
apps/
  studio/{main,preload,renderer,workers}/
  player/{main,preload,renderer}/
  tools/{cli,mcp}/
packages/
  schema/
  validation/
  core/
  project-service/
  runtime-service/
  presentation/
  ui/
examples/academy-demo/
tests/{contracts,fixtures,integration,e2e}/
docs/
```

이 구조는 목표입니다. 현재 apps/tools/cli·apps/player·apps/studio와 schema·validation·project-service·core·runtime-service·player-service·studio-service를 구현했습니다. 6단계에서 독립 Electron 편집기를 추가했습니다. 구체적인 경계는 [코어 문서](core.md), [런타임 문서](runtime.md), [플레이어 문서](player.md), [편집기 문서](studio.md)를 따릅니다.

## 모듈 경계

`schema`는 콘텐츠 형식의 원본입니다. 빌드가 스키마로부터 TS 타입을 생성하며 독립적으로 손작성한 콘텐츠 타입과 이중 관리하지 않습니다. `validation`은 구조 검사에 참조·기간·대본 검사를 추가합니다.

`core`는 콘텐츠 묶음, 현재 상태, 명령을 받아 다음 상태와 처리 기록을 반환합니다. React·Electron·파일 시스템·시스템 시각에 의존하지 않습니다. 난수도 명시적인 상태로 취급합니다.

`project-service`는 문서·파일 버전·변경·저장·충돌을 관리합니다. `runtime-service`는 코어를 사용해 실행 세션·세이브·재현·시나리오를 관리합니다. 두 서비스는 플랫폼에 필요한 입출력을 주입받습니다.

목표 구조의 `presentation`은 배경·인물·대사·선택·상태 패널을 표시하며 규칙을 계산하지 않습니다. 현재 apps/player/renderer/main.tsx의 Player 컴포넌트를 독립 Player의 bootstrap과 Studio 미리보기가 공유합니다. Studio 전용 폼·표·진단은 apps/studio/renderer에 있습니다.

`player-service`는 실행 세션의 유일한 소유자인 Electron main에서 동작합니다. 화면 동작을 코어 명령으로 바꾸고 기간 종료·자동 대본 노드를 진행하며 화면용 조회 결과를 반환합니다. React는 IPC 브리지를 통해 명령을 보내고 받은 상태만 표시합니다. 파일 대화상자·경로·실제 저장은 main에 한정합니다.

CLI와 MCP는 프로젝트·실행 서비스를 호출하는 얇은 진입점입니다. MCP가 명령 문자열을 조립해 쉘을 실행하는 구조로 만들지 않습니다. 대량 시뮬레이션은 Electron의 별도 프로세스에서 수행합니다.

## 인간 편집 흐름

데이터 표에서 비용·성장량을 비교하고, 이벤트 편집기에서 대본과 조건을 함께 작성합니다. 일정 보기에서는 사건이 비거나 몰리는 시기를 확인합니다. 실행·검증 화면에서는 임의 상태로 시작하고 미발생 이유를 확인합니다.

기본 저작 방식은 표·폼·대본입니다. 관계 그래프는 보조 시각화로 두며 대규모 노드 그래프를 필수 편집 방식으로 만들지 않습니다. 스키마만으로 모든 편집 화면을 자동 생성하지 않습니다.

GUI는 알려진 필드를 손실 없이 보존합니다. 외부 변경 시 미저장 편집과 비교해 충돌을 표시하고 자동 덮어쓰지 않습니다. 초안 저장은 허용하되 실행용 콘텐츠 묶음은 실행을 막는 오류가 없을 때만 만듭니다.

## LLM과 공동 편집

LLM에는 콘텐츠 조회, 참조 조회, 버전 검사 변경, 검증, 사건 설명, 시나리오 실행, 재현 도구를 제공합니다. 모델 자체와 채팅 UI는 초기 엔진에 내장하지 않습니다.

콘텐츠를 파일로 직접 편집할 수도 있습니다. 도구 경로와 직접 편집 경로 모두 동일한 검사를 사용하며, 실행 중에는 마지막으로 생성한 불변 콘텐츠 묶음을 유지합니다. 변경한 데이터로 시험할 때는 새로운 실행 세션을 시작합니다.

## 배포와 저장

제작 도구와 게임 플레이어는 별도 배포물입니다. 플레이어에는 편집 기능과 MCP를 포함하지 않습니다. 일반 사용자에게 Node 설치를 요구하지 않도록 패키징합니다.

세이브는 게임 콘텐츠와 분리하고 콘텐츠 식별값·엔진 버전을 포함합니다. 호환되지 않는 세이브는 감지하며 자동 변환을 보장하지 않습니다. 검색 색인과 캐시는 원본에서 재생성할 수 있게 둡니다.

## 성공 기준

프로그래머 없이 활동·관계 사건·엔딩을 추가하고 원하는 조건에서 검증할 수 있어야 합니다. 인간과 LLM이 교대로 편집해도 데이터가 보존되며, 화면 실행과 화면 없는 실행은 같은 결과를 만들어야 합니다.
