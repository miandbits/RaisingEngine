# 조건 · 실행 흐름 · 규칙 디버거

새 Qt 편집기 빌드는 `dist/qt-studio-logic/RaisingStudioQt.exe`다. `Edit-Logic-Lab.cmd`로 별도 실습 프로젝트 `projects/logic-lab`를 연다. 이전 편집기 빌드와 원본 프로젝트는 그대로 유지한다.

## 1. 조건 · 효과 · 수식

**디자인 → 정책 · 행동 · 공유 한도 작업실**에서 공통 행동을 선택한 뒤 **조건 · 비교식 시각 편집**, **효과 · 계산식 시각 편집**을 사용한다. 기본 비용·효과 표도 계속 사용할 수 있다.

시각 편집기는 같은 JSON AST를 트리와 속성 폼으로 편집한다. JSON을 직접 작성하지 않아도 된다.

- 조건: 항상, 모두 충족(AND), 하나 이상(OR), 반전(NOT), 수치 비교, 플래그, 사건 완료.
- 수식: 정수 상수, 능력·자원/관계/소지품 수량 읽기, 시간 값, 더하기·빼기·곱하기, 최솟값·최댓값으로 범위 제한.
- 효과: 대상 수치 증감·지정, 플래그 설정. 수치 효과의 값에는 위 수식을 중첩할 수 있다.
- 목록: 조건·효과 추가/삭제와 실행 순서 변경. AND↔OR, 증감↔지정처럼 호환되는 종류 변경은 기존 하위 데이터가 유지된다.

**디자인 → 콘텐츠 조건 · 효과 · 수식**에서는 사건·엔딩·활동·대본·프로젝트에 이미 작성된 조건과 효과, 성공 확률 수식을 찾아 같은 편집기로 수정한다. 목록은 이름·파일·규칙 경로로 검색한다. 공통 행동에서 새 조건·효과를 만드는 경로와, 기존 콘텐츠의 규칙을 찾아 고치는 경로를 모두 제공한다.

참조가 없거나 clamp 최솟값이 최댓값보다 크면 편집 창 안에서 저장을 막는다. 프로젝트 전체의 참조·순환·호환성 검증은 기존 공통 검증 서비스가 수행한다. 편집기와 LLM이 별도의 규칙 표현을 사용하지 않는다.

소지품 수량은 정의된 최대 보유량과 0 사이여야 한다. 장착 중인 물품을 수식 효과로 없애는 것도 거부한다. 능력치의 기존 범위 처리와 달리 인벤토리 오류를 조용히 잘라내지 않는다.

## 2. 실행 시점 · 행동 흐름

**디자인 → 실행 시점 · 행동 흐름**은 두 탭으로 구성된다.

**자동 실행 규칙**에서 이름·실행 시점·실행 행동·수량·조건·대상 필터를 설정한다. 목록의 위→아래 순서로 검사한다. **행동의 조건 분기 · 연결**에서는 특정 행동의 비용·효과 이후 실행할 단계들을 만들고, 조건이 참일 때/거짓일 때 호출할 행동을 선택한다. 거짓 경로를 비우면 그 경우 호출하지 않는다.

데이터는 `gameplay.rules`, `gameplay.actions[].flow`에 저장한다. 규칙은 `condition`, `actionId`, `quantity`를 사용하고 분기 단계는 `condition`, `thenActionId`, 선택적 `elseActionId`, `quantity`를 사용한다. 분기 단계의 수량은 부모 행동의 수량과 독립적이다. 부모의 직접 비용·효과에는 부모 수량을 적용한다.

| 실행 시점 | 의미와 필터 |
|---|---|
| `periodStart` / `periodEnd` | 일정 칸의 활동 실행 시작 / 해당 칸 종료 처리 |
| `monthStart` / `monthEnd` | 월 첫 활동 시작 / 마지막 칸 종료 처리 |
| `dayStart` / `dayEnd` | 명시적으로 설정한 논리 일자별 정산 |
| `locationEnter` | 장소가 실제로 바뀐 이동 완료, 선택적 `locationId` |
| `purchaseComplete` | 구매 성공 후, 선택적 `shopId`·`itemId` |
| `relationshipChanged` | 실제 관계 수치 변화, 선택적 `characterId`·`relationshipId` |

월·일정 시작은 새 게임이나 계획 편집 자체가 아니라 실제 첫 활동 실행 시 발생한다. 최초 배치 장소는 `locationEnter`를 발생시키지 않는다. 구매 후 규칙은 성공한 구매에만 적용한다.

### 논리 일자와 실행 순서

기존 엔진의 일정 칸을 임의로 하루라고 부르지 않는다. 일자 규칙을 사용할 프로젝트는 `gameplay.ruleCalendar.daysPerMonth`를 명시한다. 값은 일정 칸 수 이상, 최대 366이며 디자이너가 정의한 고정 월 길이다. Gregorian 달력이나 실시간 시계가 아니다.

한 달을 일정 칸에 균등 분배한다. 예를 들어 월 7일·3칸이면 각 칸은 2일·2일·3일을 포함한다. 활동은 기존처럼 일정 칸 단위로 한 번 계산하고, 그 결과 상태에서 포함된 날마다 일자 시작→종료 규칙을 정산한다. 일별 애니메이션이나 매일 별도의 활동 성공 판정을 구현한 것은 아니다.

순서는 월 시작(해당 시) → 일정 시작 → 기존 일정 전 정책 → 활동 → 일정 후 정책 → 포함된 논리 일자들의 시작/종료 정산이다. 이어지는 기간 종료 처리에서 일정 종료 → 월 종료(해당 시) → 사건 검사를 수행한다.

행동 참조의 직접·간접 순환을 검증하며, 실행 중에도 중첩·실행량 제한과 같은 발생 건에 대한 중복 실행 방지를 적용한다. 후속 규칙이 실패하면 원래 구매·이동·활동 명령까지 함께 취소한다. 돈·물품·관계·난수·실행 이력 일부만 남지 않는다. 실행 이력은 저장 및 재생 검증에 포함된다.

자동 규칙이나 중첩 흐름에서 대본 사건을 재진입시키는 연결은 검증으로 막는다. 직접 행동의 기존 사건 연결은 유지한다. 사건의 등장 조건은 규칙이 변경한 능력·관계·플래그·물품을 검사하도록 작성할 수 있다.

## 3. 규칙 디버거 · 영향 분석

**디자인 → 규칙 디버거 · 영향 분석**을 연다. 이동·도킹 가능한 패널이며 별도 창으로도 사용할 수 있다.

1. Seed를 정하고 **초안으로 새 검사**를 누른다. 저장하지 않은 편집 초안도 공통 검증에 통과하면 실제 C++ 코어로 검사한다. 독립 검사 세션이므로 열린 게임 플레이어의 진행 상태를 바꾸지 않는다.
2. 행동이나 사건을 고르고 **왜 실행 / 차단?**을 누른다. 조건 트리에 각 하위 조건의 참/거짓과 실제 비교값, 데이터 위치가 표시된다. 비용·이용 장소·사건 우선순위 등 조건식 외의 차단 원인도 확인한다.
3. 장소 이동·상품 구매·행동 실행·일정 작성·활동 실행·결과 확인·사건 처리·대본 진행 명령을 한 단계씩 실행한다. **실행 순서**, **변화**, **현재 상태** 탭에서 결과를 확인한다. 실패한 명령은 상태를 보존하며 오류 위치를 표시한다.
4. **연결 · 영향**은 선택한 행동·사건을 참조하거나 그 대상이 참조하는 정책·흐름·규칙·화면 등의 직접 연결과 참조 위치를 보여준다. 완전한 도달 가능성 증명은 아니며 기존 자동 플레이 분석과 용도가 다르다.
5. **선택 대상의 조건 편집**으로 원본 조건을 수정할 수 있다. 수정 후 새 검사를 시작해야 한다. 프로젝트 버전·디스크 변경·검사 상태 버전이 맞지 않는 명령을 거부하여 오래된 상태에서 변경이 유실되지 않도록 한다.
6. **플레이 저장 불러오기**로 실제 저장을 검사한다. 공통 저장 형식의 내용·재생 결과를 검증한 후 검사 세션으로 가져온다. 변조되거나 다른 프로젝트의 저장을 무검증 상태로 주입하지 않는다.

디버거의 상태는 임의 JavaScript 모사 결과가 아니다. C++ 코어의 읽기 전용 `inspect`와 실행 결과를 사용하고, 조건 트리의 값도 코어에서 평가한다. 검사와 영향 분석은 프로젝트 파일을 저장하거나 수정하지 않는다.

## 검증

코어 검증은 `tests/gameplay/action-flows.test.mjs`, `tests/native/rule-flows.test.mjs`, `tests/native/rule-flows-wasm.test.mjs`, 디버그 서비스 검증은 `tests/native/rule-debug.test.mjs`, `tests/qt-studio/rule-debug.test.mjs`에 있다. GUI 검증은 `native/studio/logic-test.inc`에 있다.

- TypeScript 관련 회귀 51개 통과.
- 신규 흐름의 TypeScript/C++ 일치 검증 11개, 기존 C++ 회귀 21개, Wasm 검증 2개 통과.
- 디버그·브리지·Wasm 컨트롤러 묶음 5개 통과. 실제 저장 불러오기와 변조 저장 거부 포함.
- 새 Qt AST 편집·GUI 제작·디버거 검증 4개 통과(초기화·정리 포함).
- 전체 Qt 회귀 17개 통과, 실패 0개, 조건부 테스트 3개 생략. 새 예제 제작은 앞의 별도 실행으로 검증했고, 전체 회귀에서는 같은 예제를 중복 생성하지 않았다. 나머지 두 생략 항목은 기존 PM2 시설 샘플 재생성 전용이다.

실습 프로젝트의 `Logic purchase chain` 행동은 비용 5를 지불하고 `Logic reward` 행동의 보상 3을 호출한다. 구매 완료 규칙이 이 행동을 참조한다. `Logic blocked`는 돈 999999 이상 조건을 사용하므로 초기 상태에서 차단된다. 디버거에서 새 검사 → `Logic blocked` 검사로 실제 값과 차단 원인을 확인하고, `Logic purchase chain`의 연결·영향 탭에서 구매 규칙과 후속 행동을 확인할 수 있다. 이 세 행동과 연결은 Qt 폼으로 작성했다.

GUI 스크린샷은 `.cache/qt-logic-evidence/debugger.png`, 검증 자료 사본은 `docs/evidence/logic`에 보관한다.

`scripts/verify-logic.mjs`는 GUI 작성 프로젝트를 Windows·웹으로 내보내 실제 플레이를 검증한다. 집→상점→꽃 구매에서 돈 `60 − 40 − 5 + 3 = 18`을 확인했다. 상품 비용과 연결 행동의 비용·보상이 한 명령에 포함되고 상태 버전은 한 번 증가한다. 추가 검 구매 후 6이 되었으며, 실제 저장을 불러오면 전체 상태가 정확히 18인 저장 시점으로 복원되고 구매 규칙을 재실행하지 않았다. 두 플레이어 모두 통과했다. `.cache/logic/latest.json`에서 내보내기 위치를 확인한다.

실습 프로젝트는 기존 상점 화면을 재사용한다. Windows의 낮은 화면 높이에서 상점 아래쪽 상품 행과 돌아가기 버튼이 일부 겹치는 기존 배치 문제가 남아 있다. 이번 구매·저장·불러오기 경로는 동작을 확인했으며, 해당 화면의 배치 정리는 별도 UI 작업으로 남긴다.

현재 수식은 정수 연산이며 나눗셈·사용자 함수·범용 스크립트 실행은 포함하지 않는다. 직접 비용 표는 정수 단가를 사용한다. 임의의 모든 엔진 이벤트를 연결하는 플러그인 API 대신 위에 명시한 실행 시점을 지원한다. 모바일·콘솔 실기 검증은 이번 작업 범위가 아니다.
