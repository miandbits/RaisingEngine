# 6단계 인간용 편집기

> 2026-10-11 후속 구현: [콘텐츠 탐색·흐름·자동 플레이 작업실](analysis-workspace.md)을 추가했습니다. 아래 단계별 기록과 구분해 최신 기능·검증 결과를 확인하세요.

Raising Studio는 JSON을 직접 작성하지 않고 활동·사건·엔딩을 만들고 실행하는 최소 편집기입니다. 원본은 기존 계약 0.1.0의 JSON 파일입니다. 7단계의 별도 로컬 [MCP 서버](mcp.md)도 같은 StudioEditor·검증·저장 서비스를 사용합니다. 8단계에는 [Windows 설치판과 독립 MCP 런타임](distribution.md), **12개월 새 프로젝트** 버튼을 추가했습니다. 기존 **새 프로젝트**는 2개월 샘플을 유지합니다.

## 실행과 첫 프로젝트

Windows 포터블은 `release/Raising Studio-win32-x64/Raising Studio.exe`입니다. Node.js와 개발 서버 없이 실행하며 다른 곳으로 이동할 때는 폴더 전체를 복사합니다. 설치 프로그램과 서명은 8단계입니다.

개발 실행은 프로젝트 루트에서 다음을 사용합니다. Node.js 22.12 이상이 필요합니다.

```text
npm ci --ignore-scripts
node node_modules/electron/install.js
npm run studio
```

빌드만 하려면 `npm run build:studio`, 재빌드 없이 실행하려면 `npx --no-install electron dist/studio/main/index.js`, 포터블을 다시 만들려면 `npm run package:studio`를 사용합니다.

앱을 열면 기본 샘플이 읽기 전용으로 나타납니다. **새 프로젝트**를 누르고 빈 폴더를 선택하면 샘플을 복사합니다. 기존 파일이 있는 폴더는 덮어쓰지 않습니다. 이미 작업한 프로젝트는 **열기**로 선택합니다. 새 프로젝트는 빈 게임 대신 동작하는 두 달 샘플에서 시작합니다.

## 제작 흐름

1. 왼쪽 콘텐츠 목록이나 검색으로 문서를 선택합니다. **활동 비교표**에서 비용·기본 효과·성공 판정 유무를 비교하고 행을 눌러 상세 폼으로 이동합니다.
2. **+ 추가**에서 활동·사건·엔딩·인물과 고유 ID를 지정합니다. `practice`처럼 영문 소문자로 시작하고 숫자·하이픈을 쓸 수 있습니다. 문서 경로는 앱이 정합니다.
3. 폼의 이름·설명·조건·비용·효과를 편집합니다. 텍스트와 수치는 포커스를 옮기거나 Enter를 누를 때 초안에 반영합니다. 선택형 필드는 즉시 반영합니다. `+ 사용`은 선택 항목이나 빠진 필수 항목을 추가합니다.
4. 사건·엔딩은 시작 노드와 대본 노드를 편집합니다. **형식**에서 장면·대사·선택·조건 분기·효과 적용·종료를 고르고 다음 노드 ID를 지정합니다. 선택지는 문구·조건·효과·다음 노드를 가집니다. 위/아래 버튼으로 순서를 바꾸고 삭제할 수 있습니다. 상단 대본 흐름 버튼은 해당 노드로 이동합니다.
5. **검증**을 눌러 진단을 확인합니다. 파일·코드·JSON Pointer·줄·열을 표시하며 누르면 해당 문서/필드로 이동합니다. 초안의 줄·열은 메모리 문서를 두 칸 들여쓰기로 직렬화한 위치입니다.
6. **초안 저장**으로 변경을 원본 JSON에 반영합니다. **플레이 미리보기**는 저장하지 않은 초안도 검증해 실행합니다. 편집기로 돌아간 뒤 다시 미리보기를 시작하면 새로운 스냅샷으로 시작합니다.

미리보기는 Player의 동일 React 컴포넌트와 기존 시뮬레이션 코어를 사용합니다. 기본 seed는 42입니다. 편집기 안의 미리보기에는 게임 세이브 메뉴가 없으며 원본 프로젝트를 변경하지 않습니다. 정식 저장·불러오기 플레이는 독립 Player를 사용합니다.

간단한 제작 예: 새 활동 `practice`의 이름을 ‘자유 연습’으로 하고 기본 효과에 더하기·능력 자원 `skill`·고정 수치 2를 추가합니다. 사건 `greeting`은 기간 0~0, 첫 노드를 선택으로 바꾸고 선택지의 다음 노드를 `end`로 연결합니다. 엔딩 `quiet-end`는 항상 조건, 우선순위 50으로 만들면 이 활동 한 번과 나머지 휴식 일정으로 새 엔딩을 확인할 수 있습니다. 자동 UI 테스트가 이 작업을 실제 폼 조작으로 수행합니다.

## 참조와 변경 이력

오른쪽 **참조 찾기**는 선택한 활동·인물·사건·엔딩의 사용 위치를 보여 줍니다. ID를 직접 입력하면 능력·자원·플래그·관계·노드·에셋 등의 정확한 ID 참조도 검색합니다. 진단과 참조는 문서 이동을 지원합니다. ID 이름을 바꿔도 참조를 자동으로 고치지는 않으므로 참조를 확인하고 검증하세요. 노드 ID는 문서마다 같을 수 있으므로 직접 검색 결과의 파일을 함께 확인합니다.

실행 취소·다시 실행은 메모리 초안에서 최대 100개 편집 작업을 관리합니다. 저장은 이력을 없애지 않으며 저장 후 취소한 내용은 다시 저장해야 디스크에 반영됩니다. 다른 프로젝트를 열거나 다시 불러오면 이력을 초기화합니다. 문서 삭제는 확인 후 초안에만 반영하고 저장 시 실제 삭제합니다. 주 프로젝트·능력·플래그·에셋 필수 문서는 삭제 메뉴를 제공하지 않습니다.

자동 저장은 없습니다. 새 프로젝트·열기·다시 불러오기·창 닫기는 저장하지 않은 변경이 있으면 확인을 요청합니다. 취소하면 초안을 유지합니다. 에셋 폼은 매니페스트를 편집하며 실제 이미지·음원 파일은 프로젝트 내부에 별도로 넣어야 합니다.

## 저장과 외부 변경

구조 검사에 실패하는 문서는 저장하지 않습니다. 구조적으로 올바른 문서에 잘못된 참조·기간·대본 순환 등 의미 오류가 있으면 초안 저장을 허용하고 진단을 유지합니다. 미리보기는 의미 검사와 에셋 검사까지 통과해야 합니다. JSON 문법이 손상돼 읽을 수 없는 파일은 폼으로 복구할 수 없으며 원본 파일을 수정하고 다시 불러와야 합니다.

StudioEditor는 로드한 파일 바이트의 SHA-256과 문서 목록을 기억합니다. 저장 전 전체 파일의 추가·삭제·수정을 검사하고, 충돌하면 외부 파일과 현재 초안을 모두 유지한 채 중단합니다. 강제 덮어쓰기나 자동 병합은 없습니다. 초안의 필요한 내용을 확인한 뒤 다시 불러오기를 선택해야 합니다. 변경하지 않은 파일은 공백·개행을 포함해 그대로 보존하고 편집한 파일만 두 칸 들여쓰기 JSON으로 기록합니다.

다중 파일 저장 절차:

1. `.studio/pending-save.json`을 배타적으로 생성해 협력하는 편집기 사이의 저장을 잠급니다.
2. 각 변경 파일의 원본 바이트와 목표 바이트를 base64로 기록하고 동기화합니다.
3. 파일별로 다시 버전을 확인한 뒤 임시 파일 쓰기·동기화·rename으로 교체하거나 삭제합니다.
4. 모두 성공하면 복구 기록을 삭제합니다. 저장 중 예외가 생기면 알려진 원본/목표 바이트인 파일만 원상 복구합니다.

프로세스가 중단되면 다음 프로젝트 열기에서 복구 기록을 확인합니다. 기록의 프로세스가 살아 있으면 다른 저장 작업으로 보고 기다리도록 안내합니다. 프로세스가 종료됐고 모든 파일이 기록의 원본/목표 바이트 중 하나이면 전체 작업을 이전 상태로 되돌립니다. 알 수 없는 외부 변경, 손상된 기록, PID 재사용으로 살아 있는 프로세스가 확인되면 자동 복구하지 않고 오류와 기록을 남깁니다. 이때 프로젝트와 `.studio`를 함께 보존하고 수동으로 충돌을 해결해야 합니다.

이는 협력 잠금과 중단 복구이며 파일 시스템 전체의 원자적 트랜잭션은 아닙니다. 잠금을 사용하지 않는 외부 도구가 검사와 교체 사이에 쓰는 극히 짧은 경합, 실제 전원 차단·디스크 고장까지 보장하지 않습니다. 회귀 테스트는 프로세스 중단에 해당하는 부분 적용 상태와 복구 충돌을 재현합니다. `.studio`를 작업 중에 삭제하지 마세요.

가져온 그림·폰트(PNG, 스프라이트 프레임, 플러그인 가져오기의 그림)는 저장이 원자적으로 남도록 가져오는 순간 `assets/`에 내용 해시 이름으로 기록됩니다. 새로 만든 파일은 `.studio/unsaved-assets.json`에 경로·SHA-256·편집기 프로세스와 함께 남고, 그 편집기가 프로젝트를 닫거나(종료, 「저장 안 함」 포함) 다시 열거나 다른 프로젝트를 열 때 **저장된 에셋 목록에 없는 것만** 지웁니다. 비정상 종료로 남은 기록은 다음 열기에서 같은 규칙으로 정리합니다. 다른 살아 있는 편집기가 같은 파일을 가져온 경우와 내용이 바뀐 파일은 지우지 않으며, 기록을 잃으면 파일이 남을 뿐 지워지지 않습니다.

저장 경로는 고정 문서 위치와 콘텐츠 폴더 아래의 영문·숫자·하이픈·밑줄 JSON 파일로 제한합니다. 경로 이탈과 심볼릭 링크 문서 쓰기는 거부합니다. 신규 문서는 ID 기반 이름으로 만들며 기존 ID를 바꿔도 파일 이름은 바꾸지 않습니다.

## 모듈과 IPC

| 위치 | 책임 |
| --- | --- |
| packages/studio-service/editor.ts | StudioEditor, 문서 초안·revision·이력·검증·저장·스냅샷 |
| packages/project-service/transaction.ts | 바이트 버전·안전한 경로·다중 파일 기록·복구 |
| apps/studio/main/ | 프로젝트 대화상자, IPC 직렬화, 저장/미리보기, 로컬 에셋 |
| apps/studio/preload/ | 고정된 StudioBridge와 미리보기 PlayerBridge |
| apps/studio/renderer/SchemaForm.tsx | 기존 JSON Schema를 해석하는 폼, 조건/효과/노드 형식 전환 |
| apps/studio/renderer/main.tsx | 문서 탐색·활동표·이력·진단·참조·Player 미리보기 |
| apps/player/renderer/main.tsx | 독립 Player와 Studio가 공유하는 화면 컴포넌트 |

StudioBridge는 `view`, `edit`, `open`, `create`, `reload`, `validate`, `save`, `preview`를 노출합니다. `edit`는 replace/add/delete/undo/redo 명령을 받고 `revision`이 현재 편집 버전과 일치해야 합니다. 응답은 `{ view, error, notice }`이며 view에는 문서, 편집 revision, 변경 여부, 이력 가용성, 진단, 읽기 전용 여부가 있습니다. 파일 경로는 파일 대화상자와 main에서 결정합니다.

main 요청은 하나의 큐에서 처리하고 renderer도 입력과 메뉴 요청을 순서대로 보냅니다. 폼은 자신이 바꾼 필드만 최신 초안에 합치며 같은 필드가 다른 값으로 바뀌었으면 덮어쓰지 않습니다. 미리보기 스냅샷과 실행 세션은 편집 초안과 분리합니다.

renderer는 Node·파일 시스템에 접근하지 못합니다. sandbox, contextIsolation, 고정 브리지, 발신 창/프레임/URL 검사, CSP, 외부 탐색·요청·권한 차단을 적용했습니다. ASAR 안의 기본 샘플은 읽기 API로 복사하므로 포터블 환경에서도 새 프로젝트를 만들 수 있습니다.

## 검증과 다음 단계

`npm test`: 기존 128개 + 편집/저장 회귀 11개 = 139개. `npm run test:studio`: 서비스 11개 + 실제 GUI 제작 통합 1개. `npm run test:player`: 컨트롤러 5개 + 기존 실제 플레이어 통합 2개. 중복을 제외하면 총 142개 테스트입니다.

포터블 Studio 재검증 PowerShell 명령:

```powershell
$env:STUDIO_EXECUTABLE = 'release/Raising Studio-win32-x64/Raising Studio.exe'
node --test tests/studio/electron.test.mjs
Remove-Item Env:STUDIO_EXECUTABLE
```

UI 테스트는 대화상자의 선택 결과만 대체하며 편집·IPC·검증·저장·미리보기는 실제 코드로 실행합니다. 캡처는 `.cache/studio-qa`, 로그는 `.cache/stage6-*.log`에 있습니다. 기본 1360×900과 최소 1000×700 창에서 확인했습니다.

현재는 명시적 검증·저장, 노드 폼과 이동 버튼 중심입니다. 드래그 그래프, 자동 참조 이름 변경, 시나리오 GUI 실행, 파일 감시·병합 UI, 에셋 가져오기, 프로젝트별 레이아웃 저장은 후속 개선입니다. 7단계 MCP·LLM 연결을 구현했고 저장 잠금 안에서도 전체 파일 버전을 재검사합니다. MCP 저장과 충돌해도 GUI 초안은 남아 있습니다. 위 테스트 수는 6단계 기록이며 최신 검증은 [검증 결과](verification.md)를 따릅니다. 설치·서명·업데이트·깨끗한 다른 PC 검증은 8단계입니다.
