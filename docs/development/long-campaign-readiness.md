# Long campaign readiness

The October 2026 campaign work adds reusable engine capabilities. A complete automated playthrough establishes technical completion, not commercial quality or enjoyment. Keep creative projects and their media outside public engine commits.

## Implemented contracts

- **Authored calendars:** configure units per year, days per unit, and calendar labels. A year can contain 13 phases of four activity periods without changing engine code. Existing projects retain their twelve-month defaults. Schema validation, Qt controls, native and Web displays, save descriptions, and export capabilities use the same contract.
- **Web records:** configurable manual slots and rotating automatic checkpoints use IndexedDB, with load/overwrite confirmation, stale-write protection and portable backup import/export. Saves remain scoped to the game's deployment and ID. Storage failures are reported rather than silently pretending to persist. A new deployment or browser does not automatically share saves.
- **Native recovery:** a choice produces an automatic record even when it immediately traverses automatic story nodes. The Load browser remains available when only automatic records exist. Ordinary long-save restoration uses one core replay request while retaining command replay, fingerprint checks and exact final-state validation. Gallery and inspection paths retain their existing specialized behavior.
- **Rendering:** native asset paths retain their absolute location; wrapped font lines are scaled once at each display density. Web controllers register immutable content once with the bounded WASM cache and reuse same-state projections, avoiding full-story transfers for each visibility condition.
- **Phone reading:** optional authored reading order reflows text through 200%, observes safe areas and uses controls of at least 44 logical points. Grouped actions retain a primary action and put tools in a menu. Logical paragraph anchors restore the reading position when unchanged content is revisited during a session. Existing canvas layouts remain available. See [phone reading layouts](../manual/phone-reading-layout.md).
- **Compact planning:** single-character schedules can use period summaries, an activity picker with Apply/Cancel, optional first-use guidance, and reviewed reuse of the most recently confirmed plan. Reuse copies editable assignments to the draft; it does not execute them or predict future availability. It is not a library of named routines or a schedule forecast.
- **Returning to a story:** optional Recent reading records displayed dialogue and accepted responses in memory. It clears on an accepted restore or new game. [Current reminders](../manual/current-reminders.md) projects an ordered selection of existing, currently visible text and supported current-state bindings; designers can opt into displaying it after a successful restore. It is not a saved transcript or an inferred story summary. Automatic restore panels are suppressed when no selected text is currently visible; manual access still explains the empty state. Native visibility is resolved after automatic restore effects settle. Authored context and return-after-days comprehension still need design and player evaluation.
- **Portable iOS saves:** the native player offers real Files import/export, review before replacing current progress, and validation before acceptance. Web portable backups remain available. See [portable save backups](../manual/portable-save-backups.md) for limits, supported record types and provider boundaries; simulator evidence does not establish every cloud provider or physical device.
- **Long route batches:** manual selected/all checks capture immutable draft and route inputs, show progress, allow cancellation, and distinguish passed, failed, timed-out, cancelled and not-run results. Defaults are 120 seconds per route and 900 seconds overall; legacy save-time and CLI checks retain their aggregate 60-second limit. Editing marks old results stale. See [route regression](../manual/goal-route-regression.md) for storage, resource limits and process-cleanup boundaries.
- **Sampled balance:** designers can save immediate-result priority profiles, run samples, inspect resource/condition observations and replay archived limit witnesses through the existing Analysis workflow. Preferred limits are not guarantees. Reports retain their original content and profile rather than adopting later edits. See [player priorities](../manual/player-priorities.md).

Existing event queues, conditions, flags, relationships, authored screens and multi-part endings can express long campaigns without game-specific engine branches. The project must still author meaningful consequences and a recoverable fallback.

## Repeatable evidence

`node scripts/smoke-creator.mjs --web --desktop` includes calendar parity, actual browser records, immutable-content cache correctness, native choice checkpoints, automatic-only loading, rendering, first-game playthroughs and Qt authoring. GitHub's Creator journey builds and runs these on Windows and macOS; the Windows lane also tests portable and installed editor exports and uninstall preservation. The opt-in [iOS system UI regressions](ios-system-ui-regressions.md) exercise the actual Files picker, system keyboard, background return and live rotation with XCTest; they require the documented simulator and toolchain setup. Keep the exact source commit and CI run with each result. A workflow definition or a passing older revision is not current acceptance.

For each substantial game, retain the exact content fingerprint and legal command witnesses for early/middle/late saves, choices, ending selection and epilogues. Record coverage and resource trajectories across contrasting policies. Coverage of every individual branch does not establish coverage of every possible history. A bounded search that finds no witness does not prove unreachability. Performance measurements should identify the device, content size and tested path.

## Presentation refinements — 2026-10-25

Ordinary single-character column schedules that request activity descriptions or rule summaries now share one full-width detail region across periods. Players can review a period, read all authored requirements/costs/effects, and edit its draft selection before the existing progression control confirms it. This removes the repeated narrow prose scroll areas. Automatic progression labels distinguish confirming a changed draft from starting its next activity; explicit designer labels remain unchanged. Compact reading-mode planning and roster schedules keep their existing interaction. See [schedule details](../manual/schedule-details.md). Automated checks cover command isolation and text/scroll reachability; comprehension and planning comfort remain human acceptance work.

## Remaining reusable work

| Priority | Need | Generic acceptance target |
| --- | --- | --- |
| P0 for a phone release | Accept the implemented reading layouts on intended devices | Review longest text and controls at all text scales on physical phones/tablets, including live rotation, background return, keyboard/controller focus and assistive technology. Geometry tests and 44-point controls do not establish screen-reader semantics or accessibility conformance. |
| P1 | Make return context useful at every campaign stage | Use the existing session reading history and current-state reminders, then test early, middle, pending-choice and ending restores after time away. Persistent transcripts, authored recap rules, spoiler control and empty automatic panels need explicit design; do not infer saved history from the current feature. |
| P1 | Understand a long-term schedule | Build on compact planning and reviewed last-plan reuse with optional deterministic forecasts of costs, recovery and shared upkeep, plus named routines with revalidation. Mark uncertain future events and distinguish draft changes from confirmed execution. |
| P1 | Complete designer campaign audits | Build on saved priorities, sampled Balance, replay and background route batches with reusable policy suites and explicit branch/ending coverage. Keep recorded-route regression distinct from exploration of unrecorded decisions. Project-specific proof scripts are not a completed no-code audit UI. |
| Release gate | Maintain public versions | Signed packages, verified dependency/license notices, clean machines and physical devices, save migration acceptance, backup recovery and a support policy. |
| Production gate | Establish commercial quality | Independent full-length playtests, editorial and accessibility review, coherent finished art, final audio and localization QA. These need accountable human acceptance in addition to automated checks. |

Record each unresolved need with its proposed contract, supported targets, fallback, evidence and owner. Do not label a game or engine commercial-ready merely because its route and package tests pass.
