# 다인 육성 첫 계약 — roster-activities-v1

2026-10-14. 범용화 1단계의 수용 흐름. 전체 계획: universal-raising-engine-plan.md (historical internal evidence; not distributed).

## 기존 가정과 변경 범위

| 기존 가정 | 이번 처리 | 후속 범위 |
|---|---|---|
| 전역 attributes가 단일 육성 대상의 능력 | 선택적 project.roster로 대상별 수치 분리 | 관계·소지품·효과까지 범용 개체화 |
| 월별 단일 일정 | 기존 기간 경계 재사용, 한 기간의 대상별 활동 배정 | 대상별 월간 계획·비동기 활동 |
| 대본·정책의 수식은 대상 미지정 | 주인공 기준 유지, 공용 자원 공유 | 명시적 대상 표현식·사건 소유자 |
| 탐험은 한 세션 | 다인 활동의 탐험 연결은 거부 | 세션 중단·복귀 및 다인 파티 |
| UI의 능력·일정 위젯 | Windows에서 roster 설정에 따라 대상별 표시 | 개별 데이터 바인딩·웹 렌더러 |

NPC 정의와 육성 대상 상태를 구분한다. 기존 character 문서를 참조하는 members만 육성 대상이다. 첫 member는 protagonistId와 같아야 한다. 순서는 실행·난수 소비 순서로 명시적으로 보존한다.

## 프로젝트·실행 계약

`project.roster = {localAttributeIds, members:[{characterId, initialAttributes, activityId}]}`. ID·참조·초기 범위·중복을 검사한다. 초기값 누락은 프로젝트 초기값/능력 정의 기본값을 사용한다. 개별 값만 대상별 덮어쓰기를 허용한다. 최대 대상 16명, 개별 능력 64종.

`state.roster = {attributes:{characterId:{attributeId:value}}, assignments:{characterId:activityId}}`.

`assignActivities` 명령은 모든 대상의 현재 기간 배정을 한 번에 변경한다. planning/ready에서만 허용한다. 배정에는 비용이나 시간이 들지 않는다. `executeActivity`는 대상 순서대로 기존 활동 요구조건·비용·성공 판정·효과를 실행한다. 개별 능력은 해당 대상, 나머지 능력·플래그·관계·소지품은 공통 상태를 읽는다. 따라서 뒤 대상은 앞 대상이 바꾼 공용 상태를 본다. 독립 동시 계산이라고 주장하지 않는다.

전체 배정 실행은 한 트랜잭션이다. 후속 대상의 비용 부족 등 실패 시 앞 대상의 변경·공용 비용·난수까지 전부 취소한다. 성공 시 상태 버전은 한 번 증가하고 기간은 기존 결과 확인/사건 처리가 끝난 뒤 한 번 증가한다. 다음 기간에도 배정은 유지되며 실행 전 변경할 수 있다. 월말에는 기존 계획 경계로 돌아간다.

대상별 결과는 `lastActivityResult.actorResults`에 보존한다. 기존 결과의 최상위 필드는 주인공 활동과 기간 공통 규칙 결과의 호환 뷰이며 다른 대상의 수치를 합산한 값이 아니다. 공통 규칙의 changes는 대상별 결과와 별도 배열에 기록한다. 기존 전역 `attributes`의 개별 능력 값은 주인공 값과 동기화한다. 대상 미지정 조건·엔딩·정책·자유 행동은 주인공/공통 상태를 대상으로 한다.

기간 시작·종료와 범용 정책·일자 규칙은 배정 전체에 한 번 적용한다. 대상별 일자 처리나 개별 정책을 구현한 것은 아니다. 구형 식단 기능은 별도 지원 계약을 마련하기 전 다인 설정과 조합하지 않는다. 탐험을 포함한 활동은 배정에서 거부한다.

## 호환성·저장·배포

roster를 선언하지 않은 프로젝트에는 새로운 상태 필드를 추가하지 않고 기존 명령 경로를 유지한다. 기존 스키마 버전을 일괄 변경하거나 사용자 프로젝트를 자동 변환하지 않는다. 새 선택 필드를 지원하는 로더와 실행기가 필요하며, 구형 렌더러는 `roster-activities-v1` 기능 검사로 내보내기를 거부한다.

새 저장도 기존 명령 저널을 사용한다. 초기 대상 상태·배정·결과를 재생하여 전체 상태와 비교하며, 두 번째 대상의 값만 변조해도 거부한다. 프로젝트 설정 변경 후 기존 저장을 무조건 마이그레이션하지 않는다. 콘텐츠 지문이 달라지면 기존 계약대로 불일치로 거부하므로 원본 프로젝트/저장을 보존하고 새 게임으로 시험한다.

이번 플레이어 UI 수용 대상은 Windows다. 웹/모바일/콘솔의 새 다인 UI 지원은 완료로 표시하지 않는다. 자동 분석은 대상별 활동 조합을 명령으로 실행하되 분기 후보를 256개로 제한한다. 탐색 미발견은 불가능 증명이 아니다.

## 제작 흐름

Qt의 새 프로젝트 마법사 → 화면을 포함한 비주얼 템플릿(academy-visual) → 디자인 → 다인 육성 · 대상과 활동 배정 → 개별 능력 체크 → 대상 추가 및 이름·초기값·활동 지정 → 저장 → 처음부터 플레이. 활동은 기존 콘텐츠 폼에서 편집한다. 배정 적용과 실행은 구분되며 실행 전 선택을 바꾸거나 저장할 수 있다. 공용 능력의 대상별 초기값 입력은 비활성화되며 공용 초기값은 프로젝트 설정에서 편집한다.

## 검증 결과 (2026-10-14)

- 코어·기존 저장·일정·플레이어 회귀: 42/42 통과. `.cache/roster-final-tests.log`.
- Qt GUI: `rosterAuthoringRoundtrip`, `rosterPlayIntegration` 각각 통과. 최종 제작 창 수정 후 새 샘플을 다시 GUI로 생성하고 네이티브 플레이 및 Qt 플레이를 재검증했다.
- GUI 제작 방식: QtTest가 실제 새 프로젝트 마법사와 다인 육성 대화상자의 위젯을 조작했다. Undo/Redo, 저장 및 프로젝트 재열기를 검사했다. 외부 JSON 생성으로 대체하지 않았다.
- 플레이 방식: 실제 Windows SDL/RmlUi 플레이어의 선택 상자 변경·버튼 포인터 입력·F5/F9 키 입력. Qt의 실제 플레이 QAction에서도 같은 경로를 실행했다.
- 민서(검술 10, 체력 80) → 검술 수업 → 검술 18, 체력 70. 하린(검술 40, 체력 30, 스트레스 20) → 휴식 → 검술 40, 체력 60, 스트레스 0. 공용 소지금 60 → 55.
- 다음 기간에 활동을 교환해 하린의 검술만 48로 증가. 결과 저장 후 불러오기와 새 플레이어 프로세스의 불러오기에서 전체 상태 일치.
- 확률 활동에서 대상별 능력에 따른 성공 확률(1000/4000 basis points), 공유 난수 진행, 동일 seed·명령의 재생 일치. 공통 정책은 한 번 적용되고 대상 결과와 섞이지 않음.
- 잘못된 참조·초기값·중복 대상, 오래된 상태/편집 버전, 후속 대상 비용 실패의 전체 롤백, 두 번째 대상 저장 변조 거부. 자동 분석 3회 완료 및 명령 재생 일치.
- `roster-activities-v1`이 없는 Windows/웹 런타임은 내보내기 전 거부. 이번 다인 UI의 웹 지원을 뜻하지 않는다.
